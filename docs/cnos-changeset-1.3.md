# CNOS v1 — Implementation Change Set

**Context:** This document describes additions to the shipped v1 CNOS codebase. Nothing here replaces the current architecture. Every feature is additive and can be implemented independently.

**Audience:** Code agents implementing against the current `@kitsy/cnos`, `@kitsy/cnos-cli`, `@kitsy/cnos-vite`, `@kitsy/cnos-next` packages.

**Authority:** The shipped v1 spec (`cnos-spec.md`) remains authoritative for all existing behavior. This document adds to it.

---

## Phase 1: `cnos codegen` — Typed Config Access

**Priority:** Highest. This is the single biggest DX gap.

### What to build

A CLI command that reads the `schema` section of `.cnos/cnos.yml` and generates a TypeScript declaration file.

### Command

```bash
cnos codegen                           # writes to .cnos/types/cnos.d.ts
cnos codegen --out src/cnos-config.ts  # custom output path
cnos codegen --watch                   # regenerate on schema change
```

### Generated output shape

Given this schema in `cnos.yml`:

```yaml
schema:
  value.server.port:
    type: number
    required: true
  value.server.host:
    type: string
    required: true
    default: "127.0.0.1"
  value.api.baseUrl:
    type: string
    required: true
  secret.db.password:
    type: string
    required: true
```

Generate:

```ts
// Auto-generated by cnos codegen. Do not edit.
// Source: .cnos/cnos.yml

export interface CnosValueConfig {
  "server.port": number;
  "server.host": string;
  "api.baseUrl": string;
}

export interface CnosSecretConfig {
  "db.password": string;
}

export interface CnosConfig {
  value: CnosValueConfig;
  secret: CnosSecretConfig;
}

// Typed runtime wrapper
import type { CnosRuntime } from "@kitsy/cnos";

export interface TypedCnosRuntime extends CnosRuntime {
  value<K extends keyof CnosValueConfig>(path: K): CnosValueConfig[K] | undefined;
  secret<K extends keyof CnosSecretConfig>(path: K): CnosSecretConfig[K] | undefined;
  require(key: `value.${keyof CnosValueConfig}`): CnosValueConfig[keyof CnosValueConfig];
  require(key: `secret.${keyof CnosSecretConfig}`): CnosSecretConfig[keyof CnosSecretConfig];
}
```

### Runtime typed wrapper

Also generate a thin typed wrapper that re-exports `createCnos` with the typed return:

```ts
// .cnos/types/runtime.ts (generated)
import { createCnos as _createCnos, CreateCnosOptions } from "@kitsy/cnos";
import type { TypedCnosRuntime } from "./cnos";

export async function createCnos(options?: CreateCnosOptions): Promise<TypedCnosRuntime> {
  return _createCnos(options) as unknown as TypedCnosRuntime;
}
```

Developers then:

```ts
import { createCnos } from "./.cnos/types/runtime";
const cnos = await createCnos();
cnos.value("server.port"); // autocomplete, type: number
cnos.value("typo.here");   // compile error
```

### Implementation notes

- Read schema from normalized manifest.
- Map CNOS types to TS types: `number` → `number`, `string` → `string`, `boolean` → `boolean`, `object` → `Record<string, unknown>`, `array` → `unknown[]`.
- Group keys by namespace, strip namespace prefix for the interface.
- Required keys that have `default` are still typed as non-optional (the default fills them).
- Required keys without `default` remain as-is (user must define them).
- If no schema section exists, generate an empty/untyped wrapper and print a hint.
- `--watch` mode uses `fs.watch` on `cnos.yml` and regenerates on change.

### Files to add

```
packages/cli/src/commands/codegen.ts
packages/cnos/src/codegen/
  generateTypes.ts          # schema → TypeScript string
  writeOutput.ts            # write to disk
  watchSchema.ts            # watch mode
```

### Tests

- Schema with value + secret keys → correct interfaces.
- Schema with all types → correct TS type mapping.
- Empty schema → empty interfaces, hint message.
- Missing schema section → graceful fallback.
- `--watch` regenerates on file change.
- Generated types compile without errors.

## Phase 2: `cnos watch` — Development Reload

### What to build

A CLI command that watches CNOS config files and either restarts a child process or emits filesystem events.

### Commands

```bash
# Restart mode: re-spawns the child when config changes
cnos watch -- node server.js
cnos watch --workspace api --profile local -- node server.js

# Signal mode: prints changed keys to stdout (for custom integrations)
cnos watch --signal
```

### Behavior

1. Resolve workspace and profile.
2. Determine the set of files that contribute to the resolved graph: all YAML files in effective workspace roots, all `.env` files, `cnos.yml` itself.
3. Watch those files using `fs.watch` (or `chokidar` if cross-platform reliability is needed).
4. On change:
   - Re-resolve the graph.
   - Diff the new graph against the previous.
   - In restart mode: kill the child process, re-spawn with updated env.
   - In signal mode: print the changed keys to stdout as JSON.
5. Debounce: 300ms default, configurable via `--debounce <ms>`.

### Implementation notes

- Reuse `createCnos()` for re-resolution. The pipeline is stateless.
- For restart mode, reuse the `cnos run` spawn logic.
- Changed key detection: compare `resolvedGraph.entries` values.
- Watch `cnos.yml` itself — if schema/profiles/promotion changes, full re-resolve.

### Files to add

```
packages/cli/src/commands/watch.ts
packages/cnos/src/watch/
  watchFiles.ts             # determine watchable file set from resolved graph
  diffGraphs.ts             # compare two ResolvedGraphs, return changed keys
```

### Tests

- Config file change triggers re-resolve.
- Changed keys detected correctly.
- Child process restarts with new env in restart mode.
- Signal mode outputs correct JSON.
- Debounce prevents rapid re-fires.
- New file creation in watched directory triggers re-resolve.

## Phase 3: `cnos migrate` — Adoption Accelerator

### What to build

A CLI command that scans a codebase for `process.env.*` usage and generates CNOS mappings.

### Command

```bash
cnos migrate                          # interactive mode
cnos migrate --scan ./src             # scan specific directory
cnos migrate --dry-run                # show what would change, don't write
cnos migrate --apply                  # write manifest changes
```

### Behavior

1. Scan `.ts`, `.tsx`, `.js`, `.jsx` files for:
   - `process.env.DATABASE_HOST` → extract `DATABASE_HOST`
   - `process.env['DATABASE_HOST']` → extract `DATABASE_HOST`
   - `import.meta.env.VITE_API_URL` → extract `VITE_API_URL`
2. For each discovered env var:
   - Propose a logical key: `DATABASE_HOST` → `value.database.host`
   - Detect secret-like names (`_PASSWORD`, `_SECRET`, `_KEY`, `_TOKEN`) → propose `secret.*`
   - Detect public prefixes (`NEXT_PUBLIC_`, `VITE_`) → propose `public.promote` entry
3. Present an interactive summary:
   ```
   Found 12 env vars in 8 files.

   Proposed mappings:
     DATABASE_HOST     → value.database.host
     DATABASE_PASSWORD → secret.database.password
     NEXT_PUBLIC_API   → value.api.baseUrl (promote to public)
     PORT              → value.server.port

   Accept? [Y/n/edit]
   ```
4. On accept:
   - Add entries to `envMapping.explicit` in `cnos.yml`.
   - Add public entries to `public.promote`.
   - Optionally generate initial values: `cnos define value "database.host" "localhost"`.
5. `--apply` mode also rewrites source files:
   - `process.env.DATABASE_HOST` → `cnos.value("database.host")`
   - Only when the import for `@kitsy/cnos` is already present or can be added at file top.
   - Always backs up original files.

### Implementation notes

- Use a simple regex/AST-lite scanner for env var extraction. Don't depend on a full TypeScript compiler — speed matters.
- Env var to logical key convention: strip known prefixes (`NEXT_PUBLIC_`, `VITE_`), lowercase, replace `_` with `.`.
- Don't auto-apply — always interactive or dry-run by default.
- Source rewriting (`--apply`) is opt-in and creates `.bak` files.

### Files to add

```
packages/cli/src/commands/migrate.ts
packages/cnos/src/migrate/
  scanEnvUsage.ts           # regex scanner for process.env patterns
  proposeMapping.ts         # env var → logical key proposal
  applyManifest.ts          # write to cnos.yml
  rewriteSource.ts          # optional source rewriting
```

### Tests

- Scans `process.env.X` correctly.
- Scans `import.meta.env.VITE_X` correctly.
- Secret detection: `_PASSWORD`, `_SECRET`, `_KEY`, `_TOKEN`.
- Public detection: `NEXT_PUBLIC_*`, `VITE_*`.
- Dry run produces correct proposal without writing.
- Manifest update adds correct `envMapping.explicit` entries.
- Source rewrite produces correct `cnos.value()` calls.

## Phase 4: `.env` Export Bridge + Config Drift

### 4a. `.env` file export

Add a `--to` flag to `cnos export env`:

```bash
cnos export env --to .env.generated
cnos export env --public --framework vite --to .env.vite
```

This writes a standard `.env` file to disk, consumable by Docker Compose, CI, Heroku, Vercel, and any tool that reads `.env`.

Implementation: take the output of `toEnv()` or `toPublicEnv()`, format as `KEY=VALUE\n`, write to the specified path. Trivial but high-impact for interoperability.

### 4b. Config drift detection

Add `cnos drift`:

```bash
cnos drift                            # compare schema vs actual
cnos drift --workspace api            # workspace-scoped
cnos drift --profile stage            # profile-scoped
```

Output:

```
Schema vs resolved config:

  Missing (required, not defined):
    ✗ secret.db.password          (required in schema, missing in profile: stage)

  Undeclared (defined, not in schema):
    ? value.legacy.timeout         (found in values/local/app.yml, not in schema)

  Type mismatches:
    ✗ value.server.port            (schema: number, actual: string "3000")

  Defaults applied:
    ℹ value.server.host            (using default: "127.0.0.1")
```

Implementation: compare `schema` section against resolved graph entries. Report missing required keys, keys present but not in schema, type mismatches between schema type and actual value type.

### Files to add

```
packages/cli/src/commands/drift.ts
packages/cnos/src/drift/
  compareSchemaToGraph.ts    # schema vs resolved graph diff
  formatDriftReport.ts       # human-readable output
```

### Tests

- Missing required key detected.
- Undeclared key detected.
- Type mismatch detected.
- Default-applied key reported as info.
- `--to` flag writes correct `.env` format.

## Phase 5: Singleton Runtime + Internal Stream Tagging

### 5a. Singleton runtime

Add a default export to `@kitsy/cnos` that provides singleton access without explicit `createCnos()`:

```ts
// New: singleton access
import cnos from "@kitsy/cnos";

await cnos.ready();
cnos.value("server.port");  // works after ready()
```

Implementation:
- The default export is a lazy proxy.
- `cnos.ready()` calls `createCnos()` internally with default options (resolve from cwd).
- If `createCnos()` has already been called explicitly, the singleton uses that instance.
- `cnos.read()` before `ready()` throws with a clear message: "CNOS not initialized. Call await cnos.ready() first."

This is purely additive — `createCnos()` continues to work unchanged.

### 5b. Internal stream tagging

This is an internal refactor, not a user-facing feature. Add `streamId` to `ConfigEntry` and `LoaderContext` internally. Each existing loader gets a stream ID matching its plugin ID:

- `filesystem-values` entries get `streamId: "local"`
- `dotenv` entries get `streamId: "local"`
- `process-env` entries get `streamId: "env"`
- `cli-args` entries get `streamId: "env"`

This prepares the data model for v2 streams without exposing any new manifest syntax. The `streamId` appears in provenance/inspect output (enriching debuggability now) and will be used by v2 stream enablement later.

### Files to change

```
packages/cnos/src/
  index.ts                  # add default singleton export
  orchestrator/
    singleton.ts            # NEW: lazy singleton implementation
  types/
    core.ts                 # add streamId to ConfigEntry
  loaders/
    *.ts                    # add streamId to produced entries
```

### Tests

- Singleton `ready()` resolves successfully.
- Singleton `read()` before `ready()` throws clear error.
- Explicit `createCnos()` still works.
- `ConfigEntry.streamId` populated for all loaders.
- `inspect()` shows streamId in provenance.

## Phase 6: Browser Runtime (Hardcoded Surfaces)

### What to build

A lightweight browser runtime at `@kitsy/cnos/browser` that reads promoted config embedded at build time. No configurable surfaces in v1 — two hardcoded surfaces: server (everything) and browser (promoted only).

### Browser module

```ts
// @kitsy/cnos/browser
import type { LogicalKey } from "@kitsy/cnos";

const data: Record<string, unknown> = JSON.parse(
  globalThis.__CNOS_BROWSER_DATA__ ?? "{}"
);

export function read<T = unknown>(key: LogicalKey): T | undefined {
  if (key.startsWith("secret.")) {
    throw new Error(`CNOS: secret.* keys are not available in the browser.`);
  }
  return data[key] as T | undefined;
}

export function require<T = unknown>(key: LogicalKey): T {
  const val = read<T>(key);
  if (val === undefined) throw new Error(`CNOS: key "${key}" not found in browser config.`);
  return val;
}

export function value<T = unknown>(path: string): T | undefined {
  return read<T>(`value.${path}`);
}

export function toObject(): Record<string, unknown> {
  return { ...data };
}

export default { read, require, value, toObject };
```

### Build-time embedding

Add a utility to `@kitsy/cnos` that bundler plugins use:

```ts
// @kitsy/cnos/build
export async function resolveBrowserData(options?: {
  root?: string;
  workspace?: string;
  profile?: string;
}): Promise<Record<string, unknown>> {
  const cnos = await createCnos(options);
  const promoted = cnos.toPublicEnv();
  // Also include promoted values as logical keys for cnos/browser reads
  const browserData: Record<string, unknown> = {};
  for (const key of manifest.public.promote) {
    browserData[key] = cnos.read(key);
  }
  return browserData;
}
```

### Bundler plugin update

Refactor `@kitsy/cnos-vite` and `@kitsy/cnos-next` to use this utility:

```ts
// Vite plugin (simplified)
import { resolveBrowserData } from "@kitsy/cnos/build";

export function createCnosVitePlugin() {
  return {
    name: "cnos-vite",
    async config() {
      const data = await resolveBrowserData();
      return {
        define: {
          "globalThis.__CNOS_BROWSER_DATA__": JSON.stringify(JSON.stringify(data)),
          // Also inject as VITE_* for import.meta.env compatibility
          ...Object.fromEntries(
            Object.entries(await toPublicEnvWithPrefix("VITE_")).map(
              ([k, v]) => [`import.meta.env.${k}`, JSON.stringify(v)]
            )
          ),
        },
      };
    },
  };
}
```

### Files to add

```
packages/cnos/src/
  browser/
    index.ts               # @kitsy/cnos/browser entry
  build/
    index.ts               # resolveBrowserData utility
```

Update `package.json` exports:

```json

    ".": "./dist/index.js",
    "./browser": "./dist/browser/index.js",
    "./build": "./dist/build/index.js"
  }
}
```

### Tests

- Browser runtime reads promoted value → works.
- Browser runtime reads `secret.*` → throws.
- Browser runtime reads non-promoted value → undefined.
- `resolveBrowserData()` returns only promoted keys.
- Vite plugin injects correct `globalThis.__CNOS_BROWSER_DATA__`.
- Next plugin injects correct `NEXT_PUBLIC_*` env vars.

## Summary: v1 Implementation Order

| Phase | Feature | Effort | Impact |
|-------|---------|--------|--------|
| 1 | `cnos codegen` | Medium | Highest — typed DX |
| 2 | `cnos watch` | Small | High — dev loop |
| 3 | `cnos migrate` | Medium | High — adoption |
| 4a | `.env` export `--to` | Tiny | Medium — interop |
| 4b | `cnos drift` | Small | Medium — production trust |
| 5a | Singleton runtime | Small | Medium — DX convenience |
| 5b | Internal stream tagging | Small | Low visible / high strategic |
| 6 | Browser runtime | Medium | High — frontend story |

Each phase is independently shippable. Phase 1 should ship first. Phases 2-4 can be parallelized.
